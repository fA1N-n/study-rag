# План доработки Study RAG — v2 (2026-11-07)

Статус: на согласовании. После утверждения правим `docs/spec.md` под v2.

## Что меняется

Было: RAG по заранее размеченному корпусу. Стало: пользователь загружает свой неразмеченный набор документов → агент-архитектор придумывает схему разметки и правила → данные делятся на батчи → несколько агентов размечают их параллельно по правилам, спорное решает агент-арбитр, сомнительное уходит человеку → по размеченному корпусу работает RAG, а поля разметки становятся фильтрами и автофильтрами поиска.

Ориентир по объёму и оформлению — проекты одногруппников по «Большим данным»: FlowDesk (отчёт 15 разделов, 102 unit + 148 SQL-проверок, Vercel + Supabase, CI, Docker) и SkillPath AI (отчёт 11 разделов, 231 тест, публичный стенд, демо-вход без регистрации, ARCHITECTURE.md, журнал работы с ИИ, три итерации дизайна).

## Мультиагентная разметка — как устроено

| Роль | Кто | Что делает |
|---|---|---|
| Архитектор правил | LLM | По стратифицированной выборке (20–30 документов: разные источники, папки, размеры) предлагает схему полей (тип, допустимые значения) и письменные правила с примерами и порядком решения |
| Критик правил | LLM | Проверяет правила на другой выборке: где правила противоречат, где документ не попадает ни в одно значение; архитектор правит |
| Человек | UI | Смотрит и правит схему и правила, утверждает версию (human-in-the-loop) |
| Координатор | код | Делит документы на батчи (~15–20 документов по бюджету токенов), ставит в очередь, повторяет упавшие, считает стоимость |
| Разметчики A и B | 2 LLM (разные модели или промпты) | Независимо размечают батч по правилам: значения полей + уверенность + цитата-обоснование |
| Валидатор | код (zod) | Значения из словаря, семестр согласован с предметом, обязательные поля на месте |
| Арбитр | LLM | Только при расхождении A и B по ключевым полям: решает по правилам и обоим обоснованиям |
| Очередь проверки | человек | Низкая уверенность или арбитр не уверен → человек решает в UI одним кликом |

Агенты видят начало документа (frontmatter, имя и путь файла, первые 2–3 страницы), а не весь текст. Перед отправкой в LLM ФИО, телефоны и почты маскируются. Документы с чужими персональными данными получают флаг.

Метрики (идут в отчёт): согласие A и B (каппа Коэна), доля «авто / арбитр / человек», точность по полям на золотом наборе, стоимость и время на 100 документов, сравнение «один разметчик» против «двое + арбитр».

Оценка стоимости для 572 документов: ~2,5 тыс. токенов на документ × 2 разметчика + арбитр на ~20 % → ~3–4 млн входных токенов, порядка $1 на DeepSeek. Эмбеддинги всего корпуса — центы.

## Архитектура

- Next.js 16 (Vercel) + Supabase (Postgres + pgvector + FTS russian, Auth, Storage, pg_cron + pg_net) + OpenRouter.
- Загрузка датасета: из браузера сразу в Supabase Storage по подписанной ссылке (у Vercel лимит тела запроса 4,5 МБ). Форматы: zip или файлы `.md` / `.txt` / `.pdf` / `.docx` (текстовый слой; pptx и сканы — через существующий конвейер сбора).
- Долгие задачи: таблица очереди, `FOR UPDATE SKIP LOCKED`; pg_cron раз в минуту дёргает `/api/worker/tick` (по секрету), кнопка «Запустить» — сразу. Один тик обрабатывает несколько батчей параллельно и укладывается в лимит функции. UI опрашивает прогресс.
- Таблицы: `datasets`, `documents` (итоговые метки в jsonb + сгенерированные колонки для фильтров), `rulesets` (версии схемы и правил), `label_jobs`, `batches`, `labels` (каждое решение каждого агента), `chunks`, `questions`. CRUD в UI: датасеты, документы, правила.
- RAG без упрощений (как в spec): заголовок чанка из меток, гибрид FTS + вектор + RRF, rerank, переписывание запроса + автофильтры по полям схемы, соседние страницы ±1, честный отказ, сноски, стрим, история, 👍/👎.
- Фильтры в чате строятся из схемы разметки датасета — так приложение работает с любым набором, не только с нашим.

## Риски

- Лимиты бесплатных тарифов: Supabase 500 МБ БД (храним `halfvec`), функции Vercel по времени — работаем короткими тиками.
- Персональные данные одногруппников в отчётах: на публичном демо показываем только наши материалы или маскированные.
- Eval на вопросах, сгенерированных тем же типом моделей, завышает метрики — нужны настоящие вопросы от людей.
- Картинки без описаний: часть смысла слайдов потеряна; vision-проход — только если вернутся оригиналы.
